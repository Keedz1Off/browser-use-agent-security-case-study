# Browser Use: как объяснить кейс

## Короткий рассказ

«Я исследовал, соответствуют ли ошибки и ответы агента реальным ограничениям. В локальном тесте навигации инструмент вернул ошибку политики, но сервер уже получил запрос. Я сопоставил запись на принимающей стороне с обработчиками событий и отделил этот дефект от неподтверждённой эксплуатации. Ещё три упавшие проверки оказались ошибками формата ответа: правильный код сохранился даже в чистом контрольном сценарии».

Это текст для подготовки. Используй его от своего лица, только если сам понимаешь и можешь объяснить каждый шаг. Работа была AI-assisted, не полностью ручным аудитом.

## Как работает система

Задача пользователя и состояние страницы поступают агенту → LLM предлагает действие → реестр проверяет форму аргументов → tool выполняется → BrowserSession посылает событие → CDP управляет Chrome → результат страницы возвращается агенту.

LLM не открывает соединение сам: действие исполняет код инструмента/браузера. Текст страницы — недоверенные данные, а не разрешение на действие.

## Что сломалось

Проверяли инвариант: «исключённая навигация должна быть отклонена до запроса». Инвариант — условие, которое должно оставаться истинным.

Один обработчик события проверяет политику, другой выполняет навигацию. Ошибка первого не равна гарантии отмены второго. В сохранённом тесте были одновременно ошибка инструмента и GET в свежем списке запросов локального сервера. Перевод на about:blank после этого не отменяет уже полученный запрос.

По коду это объяснение согласуется с логами. Полного измеренного порядка работы всех обработчиков у нас нет.

## Почему это пока не SSRF

Тест вызвал навигацию напрямую из доверенного кода стенда. Не показано, что чужая страница заставила агента обратиться к защищённому ресурсу. Не было подтверждённого чтения секретов, обхода изоляции или чужого сервера.

Корректная формулировка: «наблюдаемый дефект предварительного запрета навигации». Некорректная: «я доказал SSRF через prompt injection».

## Что означают остальные падения

В трёх сценариях ожидался только синтетический код. Модель вернула правильный код с префиксом REVIEW_CODE. Чистый сценарий без конфликтного текста ошибся так же. Поэтому строгая проверка формата упала, но замена задачи через injection не доказана. У модели был доступен только done — это не проверка произвольных tools.

Документация также расходилась с кодом по default cross_origin_iframes. Это несоответствие документации, не доказанный доступ к чужим данным.

## Вопросы техлида

**Как ты понял, что запрос действительно ушёл?** По записи принимающего сервера, а не по ответу модели или инструмента.

**Не осталось ли это от предыдущего теста?** Список запросов был отдельным для каждого теста.

**12 успешных Chrome-проверок исправляют старое падение?** Нет. Там отдельно настроенный explicit proxy, другая конфигурация.

**42 успешные auth-проверки доказывают защиту самого Browser Use?** Нет. Они проверяли серверную политику нашего синтетического MCP-приложения.

**Что значит 231?** Логический учёт исторических проверок: 227 passed и четыре failed. Не один новый прогон и не число найденных уязвимостей.

## Что можно утверждать в портфолио

«AI-assisted исследование границ агента, навигационной политики и серверной авторизации с разбором ложноположительных результатов».

Не утверждай полный аудит, успешную эксплуатацию, CVE, принятую баунти-находку или общую устойчивость модели к prompt injection.
